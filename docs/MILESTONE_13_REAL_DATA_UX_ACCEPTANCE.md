# 里程碑 13：真实数据、多公司与查看体验验收

## 目标

在不改写真实来源数据库的前提下，把中国国家包安装到 `odoo_2601` 的隔离副本，验证以下产品边界：

1. 国家包能够与既有 Odoo 会计、联系人、附件和多公司数据共存；
2. 原生 Odoo 菜单和中国专属数据入口完整可达；
3. 合规总览、档案、风险、报告、整改和勾稽页面在常见小屏笔记本尺寸下清晰可读；
4. 真实会计数据可以形成可审计的勾稽事实，缺少外部受控来源时不会被解释为通过；
5. 普通合规用户只能读取获授权公司的数据，且不能修改只读勾稽快照。

本里程碑是工程和产品验收，不发布正式中国财税规则，也不形成纳税、申报、抵扣、缴款或违法结论。

## 隔离与数据基线

- 来源数据库始终只读，测试使用独立数据库和配套 filestore 副本。
- 来源基线包含 5 家公司、15,589 张会计凭证、44,651 条会计分录、638 个合作伙伴和 801 个附件。
- 已过账凭证日期覆盖 `2023-03-09` 至 `2026-06-30`。
- 测试插件只部署在服务器临时目录，独立 Odoo HTTP 实例只监听本机回环地址；主 Odoo 服务和业务数据库未切换代码、未升级模块、未写入测试记录。
- 仓库、日志和本文档不保存真实附件、交易明细、合作伙伴名称、服务器凭据或登录凭据。

## 安装与初始化

- 中国国家包从 `19.0.1.10.0` 升级为 `19.0.1.11.0`。
- 依赖模块 `account`、`l10n_cn` 和 `sudo_global_finance` 正常共存。
- 4 家启用中的中国财税公司各生成一份待完善档案和 7 项待确认候选义务；非中国财税公司不生成中国档案。
- 安装后仍为 7 条中国规则草稿、0 条生效规则。国家包没有借真实数据验收绕过来源治理、独立审批或专业签核门禁。

## 浏览器验收

### 原生导航

合规应用继续使用 Odoo 原生应用入口和顶部菜单。一级查看入口包括：

- 合规总览；
- 风险中心；
- 合规报告；
- 整改跟踪；
- 合规管理；
- 规则与配置。

中国专属入口位于“合规管理”，覆盖纳税人身份、受控外部数据、电子发票、数据解析、账票勾稽、增值税申报、税款缴纳和增值税四方勾稽。规则与配置继续采用 Odoo 原生列表和表单，不另造管理后台。

### 页面状态与信息层级

- 总览明确展示档案待完善、数据充分性、规则来源签核、风险数量和下一步动作。
- 档案状态条仅高亮当前状态，候选义务保持“待确认”，不会伪装为已适用义务。
- 风险、报告和整改没有记录时均显示明确空状态。
- 四方勾稽详情先展示结论和阻断原因，再展示四方来源状态、金额口径、逐项问题、建议动作与执行审计。
- 成功批次明确提示结果是执行时点快照；后续来源变化不会改写历史结果。
- 验收发现并修复四方勾稽币种字段显示英文 `Currency` 的问题，统一显示为“币种”。

### 小屏适配

固定视口覆盖：

- `1440 × 900`；
- `1366 × 768`；
- `1280 × 720`；
- `1024 × 768`。

四种尺寸均无页面级横向溢出。`1024 × 768` 下左侧应用栏自动收窄为图标，顶部菜单、结论告警、状态条和主要字段仍完整可见。数据量较大的 Odoo 原生列表可在列表容器内横向滚动，不会带动整个页面偏移。

## 真实月度勾稽

在一家公司 `2026-06-01` 至 `2026-06-30` 的真实月度样本上执行四方勾稽：

- Odoo 账务来源：3 张已过账发票凭证、4 张草稿发票凭证；
- 受控电子发票：没有当前有效数据；
- 受控增值税申报：没有当前有效数据；
- 受控税款缴纳：没有当前有效数据；
- 结果：3 项阻断、0 项金额差异、2 项复核提醒；
- 结论：`insufficient_data`，即“数据不足，不能形成四方结论”。

系统没有把缺失金额转换成零，也没有把“尚不可比较”显示为一致。问题清单分别指出缺少电子发票、申报和缴税来源，并提示补齐受控数据；账务范围限制和 4 张草稿凭证作为复核提醒单独披露。

## 事实桥接与审计

同期间临时评估读取 5 项事实：

- `cn.reconciliation.vat.conclusion_state = insufficient_data`；
- `cn.reconciliation.vat.blocking_issue_count = 3`；
- `cn.reconciliation.vat.difference_issue_count = 0`；
- `cn.reconciliation.vat.warning_issue_count = 2`；
- `cn.reconciliation.vat.detail` 保存四类来源状态、计数、稳定问题代码和审计指纹。

5 项事实均为 `complete` 质量状态，均指向同一份当前成功批次。账务、电子发票、申报、缴税和结果五类 SHA-256 指纹全部存在。测试评估在事务内回滚，不留在验收数据库。

## 多公司与权限

使用事务内临时普通合规用户验证：

- 获授权公司用户可读取本公司批次和 5 项问题；
- 仅获授权其他公司的用户搜索不到该批次和问题；
- 对其他公司批次进行直接读取会触发访问拒绝；
- 普通合规用户没有四方勾稽批次的新建和修改权限。

临时用户在事务内回滚，不留在验收数据库。

## 服务与浏览器健康

- 主 Odoo 服务在全部验收期间保持 `active`。
- 独立测试实例没有模块 `ERROR`、`CRITICAL` 或 Python `Traceback`。
- 页面无缓存刷新后，详情正常重载，应用自身没有新增浏览器警告或错误。
- 浏览器扩展自身的告警不计入 Odoo 应用错误；SSH 临时隧道中断产生的历史 `ConnectionLostError` 在连接恢复和无缓存刷新后未复现。

## 安装与升级回归

- 本地插件校验、Python 编译和 29 项独立数据契约测试全部通过。
- 从空白隔离数据库全新安装 `19.0.1.11.0`：115 个测试方法、Odoo 统计 133 项，`0 failed / 0 errors`。
- 从干净的 `19.0.1.10.0` 基线升级到 `19.0.1.11.0`：115 个测试方法、Odoo 统计 133 项，`0 failed / 0 errors`。
- 真实数据副本执行不带测试的幂等升级成功，日志没有 `ERROR`、`CRITICAL` 或 Python `Traceback`；模块版本、国家包版本和字段元数据均为 `19.0.1.11.0`，真实会计凭证及分录数量保持不变。

### 测试执行边界

Odoo 的 `account` 测试基类假设在专用空白测试数据库中创建测试公司、用户、联系人和会计配置。把完整测试套件直接叠加到已有多公司业务数据副本，会使官方测试基类触发现有讨论频道、联系人和公司规则，并让固定测试主体与既有配置发生碰撞。这类失败不能作为插件升级失败或业务数据异常的证据。

因此发布门禁明确拆分为：

1. 真实数据副本只执行幂等模块升级、真实读取、权限、事实桥接和浏览器验收；
2. 全量自动化测试只在专用空白数据库执行；
3. 同时保留一条上一版本干净基线的升级回归路径。

本次曾在真实副本尝试运行完整套件，出现 4 个固定测试数据断言失败和 2 个 Odoo 官方测试基类跨公司初始化错误；随后按上述正确边界重新执行，真实副本无测试升级成功，干净安装和干净升级两条自动化路径全部通过。后续不得把业务副本上的 Odoo 测试基类结果误判为产品结论。

## 尚未完成

- 尚未治理和发布首批正式中国财税规则；必须补齐官方原文快照、内容哈希、独立复核和真实中国财税专业签核。
- 当前真实样本没有受控电子发票、申报和缴税数据，因此本里程碑只验证了保守的数据不足路径，没有验证真实金额一致或差异路径。
- 当前账务口径仍是 Odoo 发票税额合计，尚未建立增值税控制科目、未开票、视同销售、进项转出及其他申报调整映射。
- 尚未完成大批量并发队列和长期间压力测试；本次月度样本不能代表全库性能上限。
- 风险金额、增值税调节表和正式报告仍需在首批治理规则及真实受控外部数据具备后继续完善。
- 可选 `sudo_country_pack_cn_einvoice_xbrl` 仍需独立完成 Odoo 运行时安装和升级验收。

因此，本里程碑证明当前中国国家包可以安全安装到真实会计数据副本，并能以清晰、保守、可审计的方式暴露数据不足和下一步动作；它不代表中国财税合规包已经完成或可以替代专业税务判断。
