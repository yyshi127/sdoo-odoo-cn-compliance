# 里程碑 12：勾稽事实与合规闭环桥接

## 目标

把里程碑 09 的账票勾稽和里程碑 11 的增值税期间四方勾稽接入 `sudo_global_finance` 通用闭环：

`受控勾稽 -> 不可改写事实快照 -> 治理规则 -> 风险 -> 人工复核 -> 整改 -> 正式证据 -> 精确期间复扫 -> 关闭`

本里程碑不直接把勾稽问题伪装为法律风险。勾稽批次是数据和诊断产品；只有经过官方来源治理、测试、独立审批及中国财税专业签核的生效规则，才可以由通用规则引擎生成正式风险。

## 版本与交付

- 中国国家包版本：`19.0.1.10.0`。
- 新增 10 项勾稽事实定义。
- 新增 2 条内部控制规则草稿和 4 个正反测试案例。
- 新增勾稽批次精确期间扫描入口。
- 新增勾稽类整改任务精确期间验证复扫。
- 新增 `19.0.1.10.0` 升级迁移，刷新国家包能力并以 `Command.link` 补充草稿规则来源，不覆盖现有来源关联。

## 事实契约

### 账票勾稽

- `cn.reconciliation.einvoice.source_state`
- `cn.reconciliation.einvoice.data_gap_case_count`
- `cn.reconciliation.einvoice.unresolved_case_count`
- `cn.reconciliation.einvoice.decision_integrity_mismatch_count`
- `cn.reconciliation.einvoice.detail`

未完成复核事项只计算 `suggested`、`ambiguous` 和尚未人工复核的 `unmatched`；`reviewed_unmatched` 在详情快照中独立披露，不会被错误当成已匹配。确认后 Odoo 凭证发生变化时，完整性异常作为独立事实进入扫描。

### 增值税四方勾稽

- `cn.reconciliation.vat.conclusion_state`
- `cn.reconciliation.vat.blocking_issue_count`
- `cn.reconciliation.vat.difference_issue_count`
- `cn.reconciliation.vat.warning_issue_count`
- `cn.reconciliation.vat.detail`

详情快照保留四类来源状态、记录数量、可用金额、五类逐项差异、稳定问题代码、影响记录数和五类 SHA-256 指纹。缺失金额保持 `null`，不会转换为零。不同比较链可能引用同一税额，因此系统不汇总“差异总额”，也不把差异自动解释为少缴税或违法。

## 选择与完整性门禁

每个提供器只读取：

1. 同一合规档案；
2. 与评估完全相同的开始和结束日期；
3. 状态为 `succeeded` 的唯一当前批次。

以下情况禁止形成可通过事实：

- 评估没有完整期间；
- 没有完全相同期间的当前成功批次；
- 同期间存在排队中或处理中的新批次，此时旧结果标记为 `stale`；
- 同期间异常存在多份当前成功结果；
- 引擎版本、完成时间、来源快照或结果校验和缺失；
- 批次保存计数与当前只读子记录不一致；
- 四方结论与阻断、差异问题数量不一致。

提供器不会选择“最接近”期间，不会合并重叠批次，也不会在多个结果之间静默求和。事实快照保存来源模型和批次 ID，授权用户可从评估结果回到原生 Odoo 批次表单。

## 精确期间扫描

通用合规总览默认扫描当前财年至今天，而增值税及账票勾稽通常按月或按申报期执行。为避免把月度事实错误套用到年度累计期间，本里程碑在两类当前成功批次表单增加原生按钮 `发起规则扫描`。

该入口只选择引用对应勾稽事实的当前生效规则，并使用批次的精确期间创建评估。若档案未启用、没有正式生效规则、批次不是当前成功结果，或已有其他评估正在执行，系统明确拒绝操作。草稿规则不会因此被绕过发布门禁。

勾稽规则形成的整改任务在提交复核后，会使用原风险评估的精确期间排队验证扫描。若规则已发布新版本，复扫使用评估日当前生效且仍引用相同勾稽事实的版本；通用核验仍要求新评估通过、来源没有警告，并在高风险且要求证据时至少存在一份已验证正式证据。

## 规则治理

新增草稿：

- `CN-DATA-EINV-RECON-001`：期间账票勾稽复核准备度。
- `CN-DATA-VAT-RECON-001`：增值税期间四方勾稽复核准备度。

两条规则只描述内部数据准备和复核控制。它们关联官方网址候选来源，但候选来源没有受控原文快照、内容哈希、独立复核或专业签核，因此规则版本保持 `draft / pending`，不会进入正式评估。安装后的中国规则总数为 7，生效规则数为 0。

## 端到端测试

运行时用例通过正常治理动作临时建立测试来源和测试规则，不使用 SQL 或上下文伪造规则状态：

1. 创建官方来源测试快照并计算 SHA-256；
2. 由独立审批角色批准来源；
3. 创建四方勾稽测试规则并运行正反案例；
4. 由独立中国财税专业测试角色完成带证据哈希的专业签核；
5. 规则审批并生效；
6. 缺少外部来源的四方勾稽形成 `insufficient_data`；
7. 从批次发起精确期间扫描并生成高风险结果；
8. 创建整改任务并提交复核；
9. 补齐电子发票、申报和缴税受控来源，新成功批次替代旧批次；
10. 整改任务发起同一期间复扫，结果变为 `pass`；
11. 提交并验证正式整改证据；
12. 整改任务以 `verified / done` 关闭并保存审计事件。

测试事务回滚后，测试来源、测试规则和测试专业签核均不会留在安装数据库。

## 尚未完成

- 尚未治理并发布首批正式中国财税规则；这需要官方原文快照、独立来源复核和真实中国财税专业人员签核。
- 当前四方账务口径仍是 Odoo 发票税额合计，尚未建立增值税控制科目、税种税目和申报调整映射。
- 勾稽完成后，底层账务或外部规范化记录发生变化不会改写历史批次；只有新批次进入排队或处理后，事实适配才会把旧成功结果标记为 `stale`。当前仍依赖用户或后续自动触发器及时重新勾稽，尚未实现所有来源变化的自动失效通知。
- 尚未形成完整增值税申报调节表，也没有经专业规则计算的税务影响金额。
- 尚未在 `odoo_2601` 真实数据副本完成大数据量性能、并发队列、浏览器和人工查看体验验收。
- 风险中心需要进一步把逐项差异、期间、责任人、截止日期和下一步动作做成更清晰的查看界面。
- 可选 `sudo_country_pack_cn_einvoice_xbrl` 仍需独立完成 Odoo 运行时安装与升级验收。

因此，本里程碑证明勾稽结果已经能够保守、可审计地进入通用风险整改闭环，不代表中国财税合规包已经完成，也不构成任何税务合规、申报、抵扣、缴款或违法结论。
