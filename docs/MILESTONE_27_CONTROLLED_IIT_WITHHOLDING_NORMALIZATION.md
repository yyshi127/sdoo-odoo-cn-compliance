# M27 中国个人所得税扣缴申报受控标准化台账

交付版本：`sudo_country_pack_cn 19.0.1.24.0`。

## 1. 目标与决策

M27 为中国个人所得税扣缴申报建立独立、不可直接改写、可追溯的标准化来源台账，补齐 `CN-IIT-WHT` 候选义务到真实外部申报事实之间的数据入口。

本里程碑先建立严格的数据和隐私边界，不尝试从会计科目名称猜测工资、社保、公积金或个人所得税金额。真实数据隔离副本已安装 `hr` 和 `hr_expense`，但未安装 `hr_payroll`，仅有 1 名员工、0 笔费用，不能支撑可靠的逐人薪税计算。因此当前交付只封存企业依法取得的来源申报值，不生成工资单，不计算扣除、税率、应扣税额或法定截止日，也不形成个人所得税合规结论。

## 2. 官方制度与表单参考

本里程碑的数据语义参考以下税务机关公开材料：

- [国家税务总局关于发布《个人所得税扣缴申报管理办法（试行）》的公告](https://www.chinatax.gov.cn/n810219/n810744/n3752930/n3752974/c3963396/content.html)：明确全员全额扣缴申报、所得项目、累计预扣方法和涉税信息保密要求。
- [《个人所得税扣缴申报表》及填表说明](https://guangdong.chinatax.gov.cn/gdsw/dgsw_gkwj/2022-03/30/42d08dfa677b4ae990afc467d07ceb86/files/bf4d20b8c8104b36b76abb01ab409fce.pdf)：用于确认本期、累计、扣除和税款计算来源字段的业务含义。
- [《个人所得税基础信息表（A 表）》](https://shanghai.chinatax.gov.cn/bsfw/xzzx/bgxz/sbzsl/202402/t470788.html)：用于确认人员基础信息属于独立、敏感的申报资料。

这些链接是本里程碑的设计参考，不是已经封存、独立审批或真人专业签核的规则依据。M27 没有把页面内容预填为已治理官方来源，也没有发布任何个人所得税法定规则。

## 3. 受控契约

内部契约继续使用 `sdoo.cn.tax-data.v1`，新增数据集类型 `iit_withholding`。这不是税务机关接口、官方导出格式或申报软件兼容承诺。

申报头保留：

- 扣缴义务人名称、统一社会信用代码、所属期间、币种和主管辖区；
- 纳税年度、申报频次、申报表类型、申报状态、申报时间、参考号和更正引用；
- 来源声明的申报人数和明细行数；
- 收入、免税收入、减除费用、专项扣除、专项附加扣除、其他扣除、捐赠扣除、应纳税所得额、应纳税额、减免税额、已缴税额和应补退税额汇总。

受限人员明细保留：

- 受控源明细键和受控人员假名键；
- 居民身份状态和八类所得项目；
- 本月或本次收入、免税收入、减除费用、专项扣除及其他扣除；
- 累计收入、累计减除费用、累计专项扣除、累计专项附加扣除及累计其他扣除；
- 捐赠扣除、应纳税所得额、来源税率或预扣率、速算扣除数、应纳税额、减免税额、已缴税额和应补退税额。

契约强制：

- UTF-8 JSON、严格字段白名单、重复 JSON 键拒绝、声明记录数量一致；
- 单文件不超过 20 MiB，最多 10,000 份申报，每份最多 10,000 条受限明细；
- 同一申报中的源明细键唯一；
- `source_line_key` 和 `subject_key` 只能是 `hmac-sha256:<64 位小写十六进制>`，或由随机 UUID、32 至 64 位小写十六进制构成的受控 `opaque:<令牌>`；
- 源明细键中出现 15 位或 18 位身份证件号码会被直接拒绝；
- 姓名、证件号码、手机、地址、银行账户等未定义人员字段会被严格未知字段检查拒绝。

示例见 `docs/samples/cn_iit_withholding_contract_v1.example.json`。示例中的 HMAC 和不透明令牌均为虚构值，不得用于真实环境。真实 HMAC 密钥必须在契约之外受控保存，不能写入 JSON、Odoo 附件、日志或代码仓库；密钥应按公司或受控来源隔离，不能跨客户复用形成可关联人员标识。

`payable_refundable_amount` 只保留来源提供的有符号值。来源适配器必须在 `source_schema` 对应规范中说明正负号含义；M27 不根据符号自动认定应补、应退、可退税资格或已缴状态。

## 4. 零值、缺失与质量结论

申报头和每条明细均使用独立 `has_*` 标志区分“来源明确申报为零”和“来源没有提供字段”。零值进入规范化结果和 SHA-256；缺失字段不被静默替换为零。

以下情况形成数据错误：

- 纳税年度、主体、期间、币种或必要申报类型无效；
- 缺少申报人数、明细行数、收入合计或应补退税额合计；
- 申报人数与唯一假名人员数量不一致；
- 声明明细行数与实际明细数量不一致；
- 明细既无本期收入也无累计收入，或缺少应补退税额；
- 契约、原件完整性或公司上下文不满足受控导入条件。

以下情况形成显式复核警告：

- 来源申报状态、申报频次、居民身份或所得项目无法识别；
- 来源声明已申报但没有申报时间或参考号；
- 汇总收入与全部明细本期收入之和不一致；
- 汇总应补退税额与全部明细应补退税额之和不一致；
- 非补退税金额为负数，或来源税率、预扣率不在 0 至 1 之间。

这些校验只判断内部契约和来源字段是否可用，不重新计算税额，也不把汇总一致解释为申报正确。

## 5. 审计与不可改写性

受控导入保留输入附件 SHA-256、数据集封存 SHA-256、契约 SHA-256、规范化输出 SHA-256、单份申报 SHA-256 和每条受限明细 SHA-256。

导入运行、申报头和受限明细只能由进程内受控标记创建；普通 ORM 创建、修改、复制和删除均被拒绝。失败重跑不会替代上一份成功结果；成功重跑沿用既有版本链，把旧结果标记为非当前结果而不改写历史内容。

## 6. 隐私、权限与多公司

个人所得税扣缴来源可能包含高敏感人员信息，M27 采用比增值税和企业所得税更严格的访问边界：

- 原始 `iit_withholding` 外部数据集、附件、导入运行、申报头和明细只向合规管理员开放；
- 普通合规用户即使具有一般外部数据只读权限，也不能搜索或直接读取个税扣缴来源；
- 合规管理员仍只能读取当前允许公司的记录，跨公司搜索和直接访问均被记录规则拒绝；
- 标准化模型没有姓名、身份证件、手机号、地址或银行账户字段；
- 源明细键和人员键均不接受自由文本，防止错误信息经问题提示、搜索、导出或日志二次扩散。

原始依法取得的申报附件可能天然包含人员信息，因此其取得依据、保留期限、访问人员、独立复核和替代版本仍必须在外部数据集流程中治理。标准化脱敏不能替代原始资料的数据安全管理义务。

## 7. Odoo 原生查看体验

新增管理员菜单“合规 -> 个税扣缴申报台账”，继续使用 Odoo 原生列表、搜索、分组、徽章、表单、页签和公司上下文。

列表直接显示纳税年度、频次、申报期间、扣缴义务人、申报状态、人数、收入、应补退税额、质量状态和当前结果。表单明确提示“来源值、非自动计算、非合规结论”；受限人员明细单独放在管理员页签。明细表单隐藏来源未提供的金额字段，明确为零的字段继续显示为零，并保留字段是否提供的布尔标志。

规则与配置界面没有引入独立前端或平行菜单体系。

## 8. 升级策略

版本 `19.0.1.24.0` 使用增量后迁移，只刷新国家包版本和能力元数据。新增模型、字段、ACL、公司记录规则和视图由 Odoo 模块升级创建，不修改会计凭证、会计分录、既有外部来源、历史勾稽、规则状态或专业签核状态。

## 10. 明确边界与下一步

M27 不交付：

- 自然人姓名、证件、手机号、地址或银行账户台账；
- 工资单、薪酬计算、专项附加扣除计算或个人所得税计算引擎；
- 税务机关接口、自动申报、自动扣款或官方格式兼容承诺；
- 个税扣缴申报与 Odoo 会计、工资或税款缴纳的勾稽；
- 法定截止日、适用税率、优惠、居民身份或所得性质的自动判定；
- 已治理并经真人中国财税专业签核的个人所得税规则；
- 申报成功、税额正确、足额缴税或个人所得税合规结论。

下一里程碑应先建立按公司和有效期治理的个税账务取数口径，并在具有可靠 Odoo 工资数据或受控工资汇总来源时，分别比较工资成本、应付职工薪酬、个人所得税扣缴来源和缴税本金。没有完整口径、可靠工资来源或精确期间时必须输出数据不足，不能根据科目名称或凭证摘要猜测金额。完成可解释勾稽后，才能设计数据准备度与差异复核候选规则，并继续经过官方来源快照、独立审批、测试和真人中国财税专业签核。
