# 里程碑 14：增值税控制科目与申报调整治理

## 目标

把增值税期间勾稽的账务侧从“仅汇总 Odoo 发票税额”扩展为分层、受控、可审计的账务与申报调节链：

`Odoo 发票税额 -> 增值税控制科目发生额 -> 已批准申报调整 -> 申报比较口径`

本里程碑解决的是取数范围、口径治理和差异解释，不发布中国税法结论。控制科目映射、申报调整或金额一致均不等于纳税申报正确，也不能替代中国财税专业人员复核。

## 版本与交付

- 中国国家包版本：`19.0.1.12.0`。
- 增值税期间勾稽引擎版本：`19.0.2`。
- 新增受控模型 `sudo.cn.vat.account.mapping`，管理销项和进项控制科目。
- 新增受控模型 `sudo.cn.vat.filing.adjustment`，管理精确期间申报调整。
- 新增控制科目、申报调整和勾稽详情的 Odoo 原生列表、表单、搜索与菜单入口。
- 增值税勾稽事实详情契约升级为 `sdoo.cn.reconciliation.vat-period.fact.v2`。
- 新增 `19.0.1.12.0` 后迁移，兼容旧版成功批次和国家包元数据。

## 分层取数架构

### 第一层：Odoo 发票税额

系统继续从当前公司和勾稽期间内的客户发票、销售退款、供应商账单和采购退款读取税额。只有已过账凭证计入金额，草稿凭证数量和范围作为复核问题披露。

该层用于：

- Odoo 发票与受控电子发票的账票比较；
- Odoo 发票与控制科目发生额的内部完整性比较；
- 尚未配置控制科目时的受限回退口径。

### 第二层：增值税控制科目

销项控制科目按期间内已过账分录的 `贷方 - 借方` 计算，进项控制科目按 `借方 - 贷方` 计算。系统只读取当前公司、当前期间和已核验映射对应的总账分录，并设置单次读取安全上限。

控制科目口径必须同时具备销项和进项角色，且每份映射覆盖完整勾稽期间。一个角色可以配置多个控制科目，但同一科目在重叠期间不能存在多份已核验映射。

### 第三层：已批准申报调整

申报调整必须与勾稽开始日和结束日完全一致。增加申报口径记为正数，减少申报口径记为负数，分别按销项或进项汇总：

- `销项申报比较口径 = 销项控制科目发生额 + 已批准销项调整净额`；
- `进项申报比较口径 = 进项控制科目发生额 + 已批准进项调整净额`。

未开票收入和视同应税事项只能调整销项税额；进项税额转出只能减少进项税额申报口径。确认时点、红字、政策调整和其他受控调整可以按实际事实选择口径，但仍须经过证据和审批门禁。

### 第四层：外部受控来源比较

- 电子发票比较始终使用 Odoo 发票税额，不把控制科目或申报调整混入账票差异；
- 发票与控制科目差异独立显示，用于识别未开票、手工总账、红字、认证时点和跨期事项；
- 增值税申报比较使用“控制科目发生额加已批准调整”的申报比较口径；
- 申报应纳税额与有效缴税、冲正及退库净额继续独立比较。

不同链路可能引用相同金额，系统不会把各项差异简单相加为“总风险金额”。

## 控制科目治理

每份映射保存：

- 合规档案、公司、国家和 Odoo 会计科目；
- 销项或进项角色；
- 有效开始日和结束日；
- 配置依据引用、映射口径与限制；
- 系统内非空二进制工作底稿；
- 配置人、核验人、核验时间和 SHA-256 完整性指纹；
- 同人复核时不少于 20 字的受控例外理由。

只有合规管理员可以核验或撤销核验。受控字段变化会自动退回待核验并清除旧指纹；工作底稿内容、会计科目代码、名称或类型变化会形成完整性异常。已经进入历史勾稽范围的映射不可删除。

多公司记录规则限制用户只能读取获授权公司的映射。中国档案不能引用其他国家档案或其他公司的会计科目。

## 申报调整治理

每份调整保存：

- 合规档案、公司、币种和精确期间；
- 销项或进项口径、增加或减少方向、调整类型和正数金额；
- 调整原因与计算过程、工作底稿引用和证据附件；
- 编制人、审批人、审批时间和 SHA-256 完整性指纹；
- 同人审批时不少于 20 字的受控例外理由。

只有合规管理员可以批准或取消。已批准和已取消记录均不可修改或删除；取消不会改写已经完成的历史批次，只会从后续新批次中排除。系统拒绝空证据、非二进制证据、非正数金额和语义不一致的调整类型。

## 保守启用门禁

系统不会自动猜测企业科目，也不会因国家包安装而自动生成控制科目映射。

- 没有任何有效控制科目或申报调整时，继续使用 Odoo 发票税额，并生成“仅发票税额口径”复核提醒；
- 待核验映射和待审批调整不进入金额，系统单独提示其被排除；
- 只有一个科目角色、映射只覆盖部分期间、配置完整性失效、调整完整性失效或重复科目角色时，账务来源标记为阻断；
- 账务来源阻断时，不执行账务与申报金额比较，不把发票税额静默替代为正式申报口径；
- 控制科目和申报调整全部满足门禁后，才切换到控制科目口径。

部分期间映射仍进入批次的检查关系和问题清单，便于追溯具体配置，但其分录不会进入金额计算。

## 审计快照与事实桥接

成功批次保存并校验：

- Odoo 发票凭证关系和账务快照指纹；
- 本次检查的已核验控制科目映射；
- 实际进入金额计算的控制科目分录；
- 本次采用的已批准申报调整；
- 发票、控制科目、调整和申报比较口径的分层金额；
- 电子发票、申报、缴税和最终结果指纹；
- 稳定问题代码、严重程度、差异两侧标签和下一步建议。

为避免用于未来期间的映射调整改变历史页面含义，系统额外固化小型账务口径配置快照及独立 SHA-256。快照保存当时的映射元数据、核验指纹、期间覆盖状态、已批准调整和分层金额，不重复保存海量总账明细。事实适配器会核对快照哈希，以及其中映射、调整身份与批次关联关系。

规则事实详情 v2 新增账务口径、映射数、控制科目分录数、调整数、分层金额及发票与控制科目差异。事实适配继续要求同一档案、完全相同期间、唯一当前成功批次和完整审计指纹。

旧版 `19.0.1` 引擎成功批次在升级时标记为 `invoice_tax_totals`，并从原账务比较金额回填发票税额字段。迁移不重算历史来源、不改写原结果指纹。真实会计数据副本上的既有成功批次升级后金额和结果校验和保持不变。

## 原生查看体验

- “规则与配置”提供增值税控制科目映射入口；
- “合规管理”提供增值税申报调整入口；
- 表单使用原生状态条、核验或审批按钮、完整性状态和证据附件；
- 四方勾稽详情按“发票 -> 控制科目 -> 申报调整 -> 申报比较口径”展示金额；
- 控制科目映射、实际总账分录和申报调整在同一只读页签中可追溯；
- 待处理、阻断、差异和下一步动作继续使用 Odoo 原生告警、徽章和问题列表表达。

规则与配置保持 Odoo 原生管理体验；勾稽详情强化信息层级，但不另建脱离 Odoo 的独立管理后台。

- 从干净的 `19.0.1.11.0` 基线升级到 `19.0.1.12.0`：123 个测试方法、Odoo 统计 141 项，`0 failed / 0 errors`，日志没有 `ERROR`、`CRITICAL` 或 Python `Traceback`。
- `odoo_2601` 隔离副本执行不带测试的版本升级成功；15,589 张会计凭证和 44,651 条会计分录保持不变，没有自动生成控制科目映射或申报调整。

测试代码和数据库仅位于服务器临时目录及 `codex_*` 隔离数据库，未部署到业务数据库或主服务插件目录。
