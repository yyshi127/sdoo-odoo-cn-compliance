# 里程碑 19：电子发票 XBRL 运行时与确定性验收

## 目标

把可选插件 `sudo_country_pack_cn_einvoice_xbrl` 从纯 Python 契约和离线样例验证推进到真实 Odoo 19 运行时，完成新装、升级、官方分类标准封存、独立子进程、后台队列、规范化台账和审计结果验收，同时消除分类标准兼容工作副本跨 Python 版本不确定的问题。

交付版本：`sudo_country_pack_cn_einvoice_xbrl 19.0.1.1.0`。基础中国包保持 `19.0.1.16.0`。

## 官方材料

官方来源为财政部会计司 2025 年 5 月 19 日发布的“电子凭证会计数据标准（推广应用版）”页面：

`https://kjs.mof.gov.cn/zt/kuaijixinxihuajianshe/dzpzkjsjbzshsd/sjbz/202505/t20250519_3964020.htm`

本插件验收对象是页面中的“全面数字化的电子发票（推广应用版）”，分类标准目录和命名空间为 `einv`。同页另有“增值税电子发票（推广应用版）”，其目录和命名空间为 `inv`，属于不同标准，不能因中文名称相近而混用。

官方 `einv` ZIP 原始 SHA-256：

`EB75E173C1315742302DF5EDF74CF9E5AED51C2733B820A3236D9CFBB7F0BD8B`

安全检查结果：13 个有效文件，展开 350,501 字节，入口文件唯一，事实命名空间与入口命名空间匹配，检测到 2 处已知 `link:roleType@roleURI` 尾空格。原始 ZIP 只作为受控附件封存，未写入 Git 仓库。

## 确定性修正

运行时验收发现，原兼容实现使用标准库 `ElementTree.write()` 重写整份 XSD。同一原始 ZIP 在 Windows Python 3.11 产生工作副本 SHA-256 `7b14a6c4...`，在 Linux Python 3.12 产生 `5fc2cd60...`。语义相同但字节不同，不满足跨运行环境可复现审计要求。

修正后的流程为：

1. 仍使用 XML 解析器验证所有 XSD、命名空间、`roleType` 语义和待修正数量。
2. 仅在显式选择 `trim_role_uri_whitespace_v1` 时，对实际 `roleType` 起始标签中的 `roleURI` 属性执行边缘 XML 空白修剪。
3. 除目标属性值外，XML 声明、命名空间前缀、属性顺序、换行、注释和其他字节保持不变。
4. 词法定位数量与 XML 语义数量不一致，或修改后语义不严格等于原值仅去除边缘空白时拒绝处理；实体编码空白、注释伪装等不能安全执行最小修改的形式不会被猜测性改写。
5. 所有文件校验完成后才统一写入工作副本，任一文件失败时不产生部分修改。

新工作副本树 SHA-256：

`59d3096c08a731789b8e318d1c83b57780f8058cb9c1f0346e37fe2ac5d3fc15`

该结果已在 Windows Python 3.11 与 Linux Python 3.12 对同一官方 ZIP 独立重放并完全一致。解析运行继续同时记录插件版本、Arelle 版本、兼容方案、修正数量和工作副本哈希，因此旧运行结果不会被静默改写。

## Odoo 运行时验收

隔离环境使用 Odoo 19、Python 3.12.3 和固定依赖 `arelle-release==2.42.1`。Arelle 及其依赖安装在临时测试目录，主 Odoo 虚拟环境、主服务和业务数据库均未修改。

完成的路径：

1. 从空数据库安装基础中国包和可选 XBRL 插件。
2. 从 `19.0.1.0.0` 升级到 `19.0.1.1.0`。
3. 在 Odoo 中登记财政部来源、上传官方 ZIP、由独立合规管理员封存并验证原始哈希与附件完整性。
4. 分别登记并封存财政部公开专票、普票实例数据集。
5. 通过 Odoo `enqueue -> _process` 启动独立 Python 子进程，工作进程离线运行并返回受限 JSON。
6. 通过 cron 的 `FOR UPDATE SKIP LOCKED` 路径领取待处理任务；新成功运行正确替代上一份成功结果。
7. 规范化结果写入只读电子发票、会计单据和借贷分录台账，原始附件和解析审计字段保留。

官方实例结果：

| 样例 | 事实数 | Arelle 警告 | Arelle 错误 | 电子发票 | 会计单据 | 借贷分录 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 增值税专用发票 | 39 | 0 | 0 | 1 | 1 | 3 |
| 增值税普通发票 | 33 | 0 | 0 | 1 | 1 | 2 |

两次运行均返回退出码 0、兼容修正数 2 和相同工作副本 SHA-256。cron 再次解析普票样例后，新运行成功，上一成功运行变为 `superseded`，当前规范化台账保持唯一。

## 自动化门禁

- 归档与 XML 安全契约：9 项。
- 规范化映射契约：4 项。
- 工作副本兼容契约：5 项。
- Odoo 运行时：17 个测试方法，Odoo 统计 21 项，`0 failed / 0 errors`。
- 静态校验强制插件运行版本等于 manifest 版本，禁止兼容函数重新序列化完整 XSD，并要求 cron 与工作进程环境隔离测试存在。

工作进程环境测试确认 `PYTHONPATH` 和任意未列入允许清单的变量不会传入子进程；仅保留必要语言、动态库、路径、时区等变量，并把 HOME 和临时目录固定到任务私有目录。真实生产运行要求 Arelle 安装在 Odoo 使用的受控 Python 环境，不能依赖临时 `PYTHONPATH`。

## 结论边界

本里程碑证明的是分类标准来源封存、XBRL 技术校验、结构化解析、队列调度和规范化台账链路可安装、可升级、可复现、可审计。它不证明企业发票来源真实，不判断可抵扣、可税前扣除、会计处理或申报是否正确，也不连接税务机关。

生产部署前仍需在维护窗口安装固定依赖、备份目标数据库、重跑官方样例、验证目标主机资源限制，并使用企业依法取得的电子凭证执行受控用户验收。正式财税风险结论仍依赖账票税款勾稽、有效规则、证据和中国财税专业人员签核。
