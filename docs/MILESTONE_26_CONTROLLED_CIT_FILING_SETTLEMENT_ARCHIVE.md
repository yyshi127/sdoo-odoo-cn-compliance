# M26 中国企业所得税受控申报与缴退税档案

交付版本：`sudo_country_pack_cn 19.0.1.23.0`。

## 1. 目标

M26 将 M23 的企业所得税来源申报、M24 的账税与缴退税勾稽以及 M25 的候选规则入口，接入通用 `sudo.compliance.filing` 申报生命周期，完成企业所得税“申报、回执、应补缴款或应退退库、证据、审计指纹”的档案闭环。

本里程碑不新建平行申报模型。菜单、权限、公司上下文、状态流转和任务关联继续使用 Odoo 原生方式；企业所得税只扩展受控来源、方向判断、封存校验和清晰的查看界面。

## 2. 为什么应补与应退必须分开

通用申报档案已有“需要付款、待付款、已付款”生命周期，它适合应补税款，但不适合退税。把退库记录标为“已付款”会同时误导业务人员、报表和审计轨迹。

M26 因此采用两个明确流程：

- `payable`：来源应补金额大于零，档案必须标记需要付款；只有应补金额与有效缴款本金一致且具有已验证缴款证据，才可调用通用“登记已付款”。
- `refund`：来源应退金额大于零，档案保持“无需付款”；只有应退金额与已退库本金一致且具有已验证退库回执，才可调用独立“封存退库回执”。
- `none`：来源明确提供应补、应退且均为零，不要求缴退税封存。
- `unknown`：应补或应退字段缺失，方向待确认并阻断准备完成。
- `conflict`：同一来源同时存在正数应补和应退，方向冲突并阻断准备完成。

系统不对两个方向轧差，利息和滞纳金也不混入税款本金。

## 3. 统一档案扩展

`sudo.compliance.filing` 新增：

- 企业所得税勾稽批次、唯一来源申报和缴退税记录关联；
- 应补、应退、实缴、冲正、有效缴款、退库、利息和滞纳金只读金额；
- 结算方向徽标；
- 退库日期和退库参考号；
- 企业所得税来源快照入口；
- 独立退库封存动作。

同一档案不能同时关联增值税和企业所得税勾稽，同一企业所得税勾稽批次只能关联一份申报档案。档案必须与批次的公司、合规档案和精确期间完全一致，并固定使用 `CN-CIT` 与 `cn_cit_return`。

## 4. 申报封存门禁

准备和提交前必须同时满足：

1. `CN-CIT` 公司级义务为适用，且在申报期间有效；
2. 义务绑定的官方来源已经独立批准、具有可发布快照且未过复核期；
3. 截止日由人员依据受控来源确认并记录计算说明，系统不按期间猜测；
4. 关联当前成功且结果完整性正常的企业所得税勾稽批次；
5. 存在唯一、当前、完整性正常、无数据错误的来源申报；
6. 来源状态为已申报、已受理或更正申报，并同时具有申报时间和参考号；
7. 档案日期和参考号与来源申报完全一致；
8. 存在已验证且指纹未变化的正式申报回执或外部受控档案证据；
9. 应补应退方向完整且不冲突，档案付款配置与方向一致。

封存 schema 为 `sdoo.cn.cit-filing-archive.v1`，包含公司、档案、期间、截止日依据、适用义务、勾稽结果、来源申报、来源金额的“是否提供”标记、正式证据及各层 SHA-256。

## 5. 缴款与退库封存门禁

两个方向都要求：

- 申报已经封存；
- 企业所得税勾稽和缴退税来源完整性正常；
- 所有标准化缴退税记录无数据错误、币种一致；
- 唯一记录时，日期和参考号必须与来源完全一致；多笔记录必须提供受控汇总参考号；
- 正式证据已验证且当前指纹与验证时一致。

应补方向额外要求应补金额与“缴款成功本金减冲正本金”精确为零差额，并至少有一笔缴款成功记录。应退方向额外要求应退金额与已退库本金精确为零差额，并至少有一笔已退库记录。

统一封存 schema 为 `sdoo.cn.cit-settlement-archive.v1`，但 `settlement_kind` 明确保存 `payable` 或 `refund`。退库动作不写入通用 `payment_state=paid`，审计事件分别使用：

- `cn.cit_filing_archive.sealed`
- `cn.cit_payment_archive.sealed`
- `cn.cit_refund_archive.sealed`

## 6. 完整性与历史状态

申报和结算分别保存 JSON 快照、SHA-256、封存时间和封存证据。普通 ORM 写入不能伪造这些字段；退库封存后日期和参考号也不可修改。

查看档案时会重新计算来源、证据当前指纹和快照校验和，显示：

- `verified`：当前内容与封存一致；
- `source_superseded`：历史内容仍可校验，但来源已被新批次替代；
- `changed`：当前可重建内容与封存校验和不一致；
- `invalid`：来源、证据或方向控制已失效；
- `unsealed`：该方向尚未封存；
- `not_required`：来源明确无应补应退。

## 7. 用户入口与界面

企业所得税勾稽结果页新增“申报缴退税档案”主按钮和档案数量统计。进入统一申报档案后：

- 顶部信息条说明截止日必须人工确认以及应补、应退独立；
- 方向缺失或冲突使用危险提示阻断；
- 申报和缴退税完整性并列显示；
- 应补、有效缴款、应退、已退库四个核心金额同屏比较；
- 缴款成功、冲正、退库、利息和滞纳金分列；
- 来源申报、缴退税记录和已封存正式证据使用原生页签查看；
- 退税场景只出现“封存退库回执”，不会出现误导性的已付款结果。

## 8. 升级策略

版本 `19.0.1.23.0` 使用增量后迁移，仅刷新国家包版本和能力元数据。新增字段与视图由 Odoo 模块升级创建，不修改会计凭证、会计分录、来源申报、缴退税记录、历史勾稽结果、规则状态或专业签核状态。

国家包 XML 元数据与 `hooks.py` 同时声明 `cit_governed_rule_candidates` 和 `cit_filing_settlement_archive`；静态校验与运行时测试固定这些能力，防止同版本再次升级时发生能力清单回退。

## 10. 明确边界

本里程碑不交付：

- 企业所得税申报接口或自动提交；
- 法定截止日自动推断；
- 税率、优惠、扣除、亏损弥补或应纳税额自动计算；
- 退税资格、退税审批或到账状态的自动认定；
- 金额一致即税务合规、申报正确或税务机关认可的结论；
- 未经中国财税专业人员复核的对外意见。

正式申报、缴款和退库状态必须来自依法取得的受控数据和正式证据。系统封存的是来源链与复核事实，不替代电子税务局、银行、国库或主管税务机关。
